# ストレージ設計書

## 1. ストレージ要件の整理

### 1.1 データ規模
- **現在の容量**: TB超（テラバイト級）
- **年間増加量**: 採用活動規模により変動（推定100-500GB/年）
- **保存期間**:
  - 採用者データ: 永久保存
  - 不採用者データ: 1-2年後削除（個人情報保護法対応）
- **ファイル数**: 数十万〜数百万ファイル
- **平均ファイルサイズ**: 1-10MB/PDF

### 1.2 アクセスパターン
- **読み取り頻度**: 高（採用担当者が頻繁にアクセス）
- **書き込み頻度**: 中（採用活動中は頻繁、それ以外は低）
- **同時アクセス数**: 最大100ユーザー
- **ピーク時間**: 平日9:00-18:00

## 2. ストレージソリューション比較

### 2.1 クラウドストレージ

#### 2.1.1 AWS S3（推奨）
**メリット**:
- **スケーラビリティ**: 容量無制限、自動拡張
- **可用性**: 99.99%の耐久性
- **コスト**: 従量課金で無駄がない
- **セキュリティ**: 暗号化、アクセス制御、監査ログ
- **バックアップ**: S3バージョニング、クロスリージョンレプリケーション
- **統合**: AWS Lambda、CloudFrontなど他サービスとの連携が容易
- **ストレージクラス**:
  - S3 Standard: 頻繁アクセス用
  - S3 Intelligent-Tiering: アクセス頻度に応じた自動最適化
  - S3 Glacier: アーカイブ用（低コスト）

**デメリット**:
- クラウド依存（ベンダーロックイン）
- データ転送料金が高額になる可能性
- インターネット接続必須

**コスト試算（東京リージョン）**:
- **ストレージ料金**:
  - S3 Standard: $0.025/GB/月
  - 1TB = $25.6/月、10TB = $256/月
- **データ転送料金**:
  - アップロード: 無料
  - ダウンロード: 最初の100GB無料、以降$0.114/GB
- **リクエスト料金**:
  - PUT: $0.0047/1,000リクエスト
  - GET: $0.00037/1,000リクエスト

**年間コスト試算（5TB想定）**:
- ストレージ: $1,280/年
- 転送料金（月100GB想定）: $1,368/年
- リクエスト料金: $100/年
- **合計: 約$2,750/年（約40万円）**

#### 2.1.2 Azure Blob Storage
**メリット**:
- S3と同等の機能
- Microsoft製品との統合が容易
- 日本にデータセンターあり

**デメリット**:
- S3よりわずかに高コスト
- AWSほどのエコシステムなし

**コスト**: S3とほぼ同等

#### 2.1.3 Google Cloud Storage
**メリット**:
- S3と同等の機能
- Google製品との統合が容易
- AI/ML機能との連携

**デメリット**:
- エンタープライズ向け実績がAWS/Azureより少ない

**コスト**: S3とほぼ同等

### 2.2 オンプレミスストレージ

#### 2.2.1 NAS（Network Attached Storage）
**メリット**:
- 一度購入すれば月額費用なし
- インターネット不要
- データ所有権が明確

**デメリット**:
- 初期費用が高額（10TB NASで100-300万円）
- スケールアウトが困難
- 保守・運用コストが必要
- バックアップ体制の構築が必要
- 災害対策が困難

**コスト試算（10TB NAS）**:
- **初期費用**: 200万円
- **年間保守費用**: 30万円
- **電気代**: 10万円/年
- **5年間総コスト**: 約400万円

#### 2.2.2 SAN（Storage Area Network）
**メリット**:
- 高性能
- 大規模対応可能

**デメリット**:
- 非常に高額（数千万円〜）
- 専門知識が必要
- 本規模には過剰

**コスト**: 採用管理システムには不適

### 2.3 ハイブリッド構成

#### メリット
- 頻繁アクセスデータ: オンプレミス（高速）
- アーカイブデータ: クラウド（低コスト）
- バックアップ: クラウド（災害対策）

#### デメリット
- システムが複雑化
- 両方の運用コストが発生

## 3. 推奨ストレージ構成

### 3.1 推奨: AWS S3ベースのクラウド構成

```
┌─────────────────────────────────────────┐
│        フロントエンド (React/TS)        │
│         （ブラウザ）                     │
└─────────────────────────────────────────┘
                    ↓ HTTPS
┌─────────────────────────────────────────┐
│     バックエンドAPI (Node.js/Express)   │
│     （EC2 or Lambda）                    │
└─────────────────────────────────────────┘
            ↓                    ↓
    ┌───────────┐        ┌──────────────┐
    │   RDS     │        │   S3 Bucket  │
    │(メタデータ)│        │ (PDFファイル) │
    └───────────┘        └──────────────┘
                                ↓
                        ┌──────────────┐
                        │  S3 Glacier  │
                        │（アーカイブ）  │
                        └──────────────┘
```

### 3.2 S3バケット設計

#### 3.2.1 バケット構成
```
raku-library-production/
  ├── active/              # アクティブな採用者データ（S3 Standard）
  │   ├── 2024/
  │   │   ├── engineering/
  │   │   │   ├── candidate-001/
  │   │   │   │   ├── resume.pdf
  │   │   │   │   ├── cv.pdf
  │   │   │   │   └── interview-notes.pdf
  │   │   │   └── candidate-002/
  │   │   └── sales/
  │   └── 2025/
  ├── archive/             # アーカイブデータ（S3 Intelligent-Tiering）
  │   └── 2023/
  └── rejected/            # 不採用者データ（自動削除設定）
      └── 2024/
```

#### 3.2.2 命名規則
- バケット名: `raku-library-{environment}` (production, staging, dev)
- オブジェクトキー: `{status}/{year}/{department}/{candidate-id}/{document-type}.pdf`

例: `active/2024/engineering/candidate-001/resume.pdf`

### 3.3 S3機能の活用

#### 3.3.1 ライフサイクルポリシー
```json
{
  "Rules": [
    {
      "Id": "ArchiveOldData",
      "Status": "Enabled",
      "Transitions": [
        {
          "Days": 365,
          "StorageClass": "INTELLIGENT_TIERING"
        },
        {
          "Days": 1095,
          "StorageClass": "GLACIER"
        }
      ]
    },
    {
      "Id": "DeleteRejectedCandidates",
      "Status": "Enabled",
      "Prefix": "rejected/",
      "Expiration": {
        "Days": 730
      }
    }
  ]
}
```

#### 3.3.2 バージョニング
- 誤削除防止
- 履歴管理
- ロールバック可能

#### 3.3.3 暗号化
- **保存時暗号化**: SSE-S3（AWS管理キー）またはSSE-KMS（カスタムキー）
- **通信時暗号化**: HTTPS必須

#### 3.3.4 アクセス制御
- **IAMポリシー**: APIアクセス制御
- **バケットポリシー**: バケットレベルの制御
- **署名付きURL**: 一時的なアクセス権限（ダウンロード用）

例: 署名付きURL生成（有効期限15分）
```javascript
const AWS = require('aws-sdk');
const s3 = new AWS.S3();

const url = s3.getSignedUrl('getObject', {
  Bucket: 'raku-library-production',
  Key: 'active/2024/engineering/candidate-001/resume.pdf',
  Expires: 900 // 15分
});
```

### 3.4 CDN（CloudFront）の活用
- PDFの配信を高速化
- グローバルエッジロケーションからの配信
- キャッシュによる転送料金削減

## 4. セキュリティ対策

### 4.1 アクセス制御
1. **IAMロール**: EC2/Lambdaに最小権限を付与
2. **VPC Endpoint**: プライベートネットワーク経由でS3アクセス
3. **MFA Delete**: 削除時に多要素認証要求

### 4.2 監査・ログ
- **S3 Server Access Logging**: アクセスログ記録
- **CloudTrail**: API呼び出しログ
- **GuardDuty**: 異常検知

### 4.3 バックアップ
- **クロスリージョンレプリケーション**: 大阪リージョンへの自動複製
- **定期スナップショット**: 週次バックアップ

## 5. パフォーマンス最適化

### 5.1 マルチパートアップロード
- 5MB以上のファイルは分割アップロード
- 並列アップロードで高速化

### 5.2 転送アクセラレーション
- S3 Transfer Accelerationを有効化
- CloudFrontエッジロケーション経由でアップロード

### 5.3 リクエスト最適化
- **プレフィックス分散**: 同時リクエスト性能向上
- **バッチ処理**: 複数ファイルの一括処理

## 6. コスト最適化

### 6.1 ストレージクラスの適切な選択
- アクティブデータ（1年以内）: S3 Standard
- 過去データ（1-3年）: S3 Intelligent-Tiering
- アーカイブ（3年以上）: S3 Glacier

### 6.2 データ転送料金の削減
- CloudFrontのキャッシュ活用
- 不要なデータ転送の削減
- リージョン内通信の活用

### 6.3 不要データの削除
- ライフサイクルポリシーで自動削除
- 定期的な棚卸し

## 7. 移行計画

### 7.1 データ移行手順
1. 既存データの棚卸し・整理
2. S3バケット作成・設定
3. AWS DataSync または CLI を使用した一括アップロード
4. メタデータの移行（RDSへ）
5. 整合性チェック
6. 本番切り替え

### 7.2 移行ツール
- **AWS DataSync**: 大量データの高速転送
- **AWS CLI**: スクリプトによる自動化
- **カスタムスクリプト**: メタデータ抽出・変換

### 8.1 監視項目

### 8.3 定期メンテナンス

## 9. まとめ

**推奨構成**: AWS S3ベースのクラウドストレージ

**理由**:
1. **スケーラビリティ**: TB級のデータに対応、今後の拡張も容易
2. **コスト効率**: 従量課金で無駄なし（年間約40万円 for 5TB）
3. **可用性・耐久性**: 99.99%の高い信頼性
4. **セキュリティ**: エンタープライズレベルの暗号化・アクセス制御
5. **運用負荷**: マネージドサービスで運用が容易
6. **バックアップ**: クロスリージョンレプリケーションで災害対策
7. **エコシステム**: AWS他サービスとの連携が豊富

- データベーススキーマ設計
- 認証・認可の仕組み検討
